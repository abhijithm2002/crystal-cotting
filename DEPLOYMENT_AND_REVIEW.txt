MAIN CAUSE
The backend sends { success: true, data: ... }. Axios puts that envelope in
response.data, but the admin screens expected the content directly in response.data.
This broke form hydration, lists, image selection, dashboard values, and editing.
The shared admin API client now unwraps content and preserves pagination separately.

OTHER FIXES

- Public content refreshes on tab focus and every 60 seconds while visible.
  Background refreshes retain the page and preserve the last successful content.
- API content bypasses caches. API origins tolerate /api and trailing slashes.
- Tab-scoped authentication survives reload when cross-site cookies are unavailable.
- Password changes/reset now affect database-backed login; startup preserves passwords.
- Startup no longer recreates deliberately deleted starter content.
- Media replacement updates page references before removing the old file.
- In-use media cannot be deleted until its references are removed.

- About/team/certificates, contact banner/socials, theme colors, footer details,

DEPLOY IN THIS ORDER
1. Backend on Render
   Deploy the modified crystalcoat-backend source. Use npm ci for build and npm start
   for start. Preserve the existing persistent MongoDB URI and JWT secret.
   Required production environment:
     NODE_ENV=production
     MONGODB_URI=<existing production MongoDB URI>
     JWT_SECRET=<existing strong secret>
     WEBSITE_ORIGIN=https://crystal-cotting.vercel.app
     ADMIN_ORIGIN=https://crystal-cotting-admin.vercel.app
   ADMIN_EMAIL and ADMIN_PASSWORD seed a new account. Existing database passwords
   now remain authoritative, including passwords changed through admin.
   If an intentional credential recovery is needed, the existing npm run reset-admin
   command resets the admin account; do not run it as a routine deploy command.
   Configure SMTP credentials and MAIL_FROM if password reset emails are required.

2. Persistent image storage — updated fix
   Set MEDIA_STORAGE=gridfs on Render and redeploy the backend.
   Production now defaults to MongoDB GridFS; originals and thumbnails persist in
   the existing MongoDB database. No paid Render disk or new storage credentials
   are needed for GridFS mode. Images count toward database storage usage.
   Existing /uploads URLs work for both old local files and new GridFS files.
   Old files already missing from Render must be reuploaded or restored from backup.
   To repair a used image, select Replace in Media Library; references are updated.
   Alternatively upload/select it in the page editor and click Save changes.
   Disk mode is still supported explicitly with MEDIA_STORAGE=disk and UPLOADS_DIR
   pointing to a persistent disk. The two modes must not be confused.

3. Admin and public website on Vercel
   Deploy the corresponding modified sources to their existing projects.
   Set the following build-time variable in BOTH projects:
     VITE_API_BASE_URL=https://crystal-cotting-backend.onrender.com
   Matching .env.production files are included. Vercel environment overrides must
   agree with them. Build with npm run build and use output directory dist.
   Redeploy after changing environment variables.
   Deploy the backend first because the public website now uses /api/media/gallery.
   Reference: https://vercel.com/docs/frameworks/frontend/vite

4. Hosted acceptance check
   Sign in, edit a homepage title, save, and focus/reload the website.
   Upload/select an image, save its section, and verify it displays.
   Test a Featured switch, gallery upload, and quote submission.
   Finally restart the backend and confirm both saved content and images survive.
   These hosted write/persistence checks are still pending deployment.

ADMIN UPLOAD AND USABILITY UPDATE — 12 October 2026
The latest reported uploaded JPG returns HTTP 200 with image/jpeg. The current
reported failure therefore concerns admin response handling, not that file's storage.
Uploads and replacements now parse the HTTP response explicitly (including JSON text),
validate the returned media, and verify that the image loads before selecting it.
Malformed responses fail clearly rather than becoming blank editable content.

The admin now provides:
- Direct Upload image buttons and image previews; no upload modal required.
- Saved images from all sections, with an availability check before selection.
- A sticky Publish changes bar for Homepage, About, Contact and Site Settings.
- Unpublished-change status, publishing confirmation, and a View website link.
- A warning when closing/reloading a page with unpublished edits.
- Dashboard task shortcuts and clearer menu/section/visibility labels.

To update the site: select the page, upload or choose an image, edit text, click
Publish changes, then View website. Gallery uploads are published automatically.
This update requires pushing/redeploying the ADMIN repository. The frontend changes
in this update are tests/documentation only; no new frontend runtime or backend
changes are required for this admin fix. Refresh the open admin tab after deployment.

Validation uses production builds, including direct image upload, thumbnail/original
loading, public homepage display after publish, selecting a saved image, a rejected
upload, dirty-state indicators, branding, quote submissions and CSV download.
Changes are uncommitted locally; no production upload/write was performed by the agent.

MISSING GALLERY FILES
The old /uploads/1789529115760-84fb5a9379496b2c.jpg still returns 404.
The public gallery now checks photos before displaying them, omits failures, and
hides the section if no photos can load. It retries on subsequent content refreshes.
No media records are deleted. In Admin > Gallery, missing images show a warning,
the original filename, and a Replace photo button. Choose the original photo to
restore it; replacement publishes automatically and retains the record/order.
Push/redeploy frontend and admin for these changes. Missing originals must be
supplied by the owner or restored from backup; code cannot recreate lost bytes.
